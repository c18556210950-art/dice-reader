# 设计说明：为什么是两阶段识别

## 背景

目标是用一张俯拍照片读取整盘 D&D 骰子的结果。最初的实现把整张图一次性发给视觉模型，让模型同时完成“找骰子、判断类型、读上表面、给出坐标”。

实测发现这条路径有两个问题：

1. **整图分辨率被云端压缩**。1600×1206 的整图在 DeepSeek 视觉接口里约合 800 个图片 token；一张六骰照片里，每颗骰子最终只分到十几到几十个 token，d10 的 0/8/4、d20 的密集数字很容易读错。
2. **随机性**。没有显式设置 `temperature` 时 DeepSeek 默认 1.0，同一张照片多次调用可能给出不同类型或读数，甚至出现越界值导致整次请求校验失败。

## 现在的流程

1. **定位**：整图发给模型，只要求返回每颗骰子的 `kind`、`value`、`bbox` 和简短说明。
2. **裁剪复核**：按 bbox（外扩 18%）从 1600px 图上裁出单颗骰子，短边不足 360px 时放大，逐颗再问一次“类型 + 上表面读数”。
3. **合并**：以裁剪结果为准；裁剪失败或返回 unknown 时回退到整图结果。坐标始终保留整图的 bbox。
4. **校验**：逐颗修复/丢弃非法值，而不是让一颗坏骰子把整次请求变成 502。

裁剪请求彼此独立，所以用线程池并发（默认 6 路）。六骰照片从约 5.5 秒降到 2.5 秒，10 颗从约 8.5 秒降到 3.7 秒。

## 实测数据（同一张六骰公开照片）

| 配置 | 结果 |
| --- | --- |
| 未设 temperature，9 次 | 3 次 502、3 次错读、3 次全对 |
| `temperature=0`，3 次 | 0 次 502、0 个错值；2 次全对，1 次红骰留空 |
| 整图 1600 与 2400 对比 | prompt_tokens 都是 1548，放大上传无效 |
| 单颗裁剪后识别 | 非 d4 的 5 颗全部正确；d4 在 3/4 之间摆动 |
| 新流程 6 路并发 | 六骰 2.2–2.5 秒；10 颗合成图 3.6–3.7 秒 |

## 百分位骰

模型被要求不合成 d100，只返回 d00 和 d10。前端负责配对：

- 每颗 d00 与 bbox 中心最近的未配对 d10 组合；
- 个位取 `d10.value % 10`（显示 0 时内部值是 10，按 0 算）；
- `00 + 0 = 100`，其余按十位 + 个位；
- 配对的两颗不再单独求和，页面显示配对行和“已配对/已并入”标记。

## BYOK（自带 API）

纯前端页面不经过本站后端，需要考虑浏览器 CORS。预检实测：

| 服务 | 浏览器直连 |
| --- | --- |
| DeepSeek | 允许本站 Origin |
| OpenAI | 允许本站 Origin |
| Google Gemini（OpenAI 兼容） | 允许本站 Origin |
| OpenRouter | `*` |
| Moonshot / Kimi | 允许本站 Origin |
| 阿里云百炼 Qwen | `*` |
| Anthropic Claude | 需要 `anthropic-dangerous-direct-browser-access: true` |
| 智谱 GLM | 只允许自家 Origin，未支持 |

BYOK 采用同样的两阶段裁剪，但并发数为 4，密钥只存浏览器。

## 取舍

- 每次识别是 `1 + 骰子数` 次模型调用，token 约为单次整图的 3 倍；换来的是多骰场景的读数稳定性。
- 不使用专门的骰子检测器，复杂遮挡和重叠仍会漏检。
- d4 的顶读/底读是规则歧义，不是模型能力问题，`auto` 模式会保守留空。
- 限流是单进程内存计数，多实例部署需要外部限流。
